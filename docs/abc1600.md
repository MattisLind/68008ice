# ABC1600 and generic memory emulation

Dispatcher 0.7 provides two distinct memory applications. The ABC1600 app
executes **105 instructions from reset: the original five plus the next 100**.
It ends in the ROM's MAC initialization loop at PC `$7E`, with 300 byte reads
and 54 byte writes. Every bus transfer, all 106 CPU snapshots and the MAC
segment/page tables match the host reference. This is an early boot milestone,
not a complete ABC1600 machine emulator.

| Application | ID | Memory behavior |
| --- | --- | --- |
| `generic-memory` (`bus-memory` compatibility name) | 4 | Uploaded image at zero, read-only image range, flat RAM elsewhere in a 1 MiB map. No ABC1600 registers or mirrors. Existing small fixture/timing modes remain available. |
| `abc1600-memory` | 7 | ABC1600 boot-ROM overlay and mirrors, task/MAGIC/BOOTE controls, segment/page registers, translated RAM, cause register and protection faults. |

Both share the PIO memory responder and state analyzer. The CPU remains a
separate app, ID 6; every target access still crosses the physical byte bus.
The [unchanged supplied ROM](../roms/abc1600/README.md) is uploaded over USB,
not embedded into the MCU firmware. See the
[recorded 105-instruction evidence](validation/abc1600-105-2026-11-17/README.md).
The earlier [five-instruction record](validation/abc1600-2026-11-17/README.md)
is retained as history.

## ABC1600 hardware behavior implemented

The functional model follows the local MAME source at commit
`2ab83c729233ca620533d692a8aa1729693ae87f`, principally
`mame/src/mame/luxor/abc1600_mmu.cpp` and its header. These files carry
BSD-3-Clause/Curt Coder notices; the port retains them and the license in
[LICENSES/BSD-3-Clause-MAME.txt](../LICENSES/BSD-3-Clause-MAME.txt).
MAME's whole-project GPL code is not linked into the firmware.

The model implements:

- The 16 KiB boot image mirrored throughout `$00000..$1FFFF` while BOOTE is
  zero. Reads see the ROM; writes below it follow MMU translation into RAM.
- Supervisor/user and program/data distinctions from FC, task-zero forcing,
  SEGA19 selection, and the task/MAGIC rules used by MAME.
- MAC registers in the upper logical half when selected: page high at offset
  0 modulo 8, page low at 1, segment at 3, task control writes at 5 and cause
  reads at 7. Unused register positions read zero/ignore writes.
- All 1024 segment bytes and 1024 page words. Page-high writes mask reserved
  bits; reads replicate X20 into the documented upper-address readback bits.
  Segment readback includes inverted MAGIC.
- Translation to 21-bit physical addresses. The first 1 MiB is physical RAM;
  the ordinary unmapped range reads `$FF` and ignores writes. NONX and the
  page write-permit bit cause BERR where MAME rejects access.
- Cause-register reset value `$02`, reset-button/PARTST state in the portable
  model, translated-access cause bits/DMAOK, and watchdog-service read counts.

Each ABC1600 RUN is a reproducible **cold start**: segment bytes `$FF`, page
words `$FFFF`, zeroed physical RAM, task/BOOTE/MAGIC/cause zero. It then pulses
RESET/HALT. The ROM's `$40` task-control write enables MAGIC while retaining
boot overlay. Its next loop programs segment and page entries through real
bus writes. The generic backend is unaffected by those address meanings.

The model uses the uploaded image at PSRAM `0x11200000`, with separate ABC1600
physical RAM at `0x11300000..0x113FFFFF`. MAC tables live in MCU SRAM. These
regions do not overlap module staging or capture rings. The generic backend
uses its existing 1 MiB target map at `0x11200000`.

## Run the 105-instruction test

```sh
make dispatcher-build
# Program each matching build/multidrop/{1,2}/dispatcher.uf2 on its board.
python3 tools/cpu_reference.py --prepare
python3 tools/abc1600_model.py
python3 tools/abc1600_check.py --cpu /dev/cu.usbmodem24401 \
  --memory /dev/cu.usbmodem24301 --allow-drive --allow-writes
```

The CPU reference uses the previously pinned, separately downloaded Musashi
source. The MAC reference uses **17 methods extracted unchanged from your
local MAME source** in a small test-only address-space shell. The test compiles
these references on the host; it does not build the complete MAME application.
Source fingerprints reject stale reference libraries.

The helper uploads/CRC-checks/reads back the ROM, verifies that malformed ABC
RUN settings are rejected, starts the CPU waiting for a physical reset, and
starts ABC1600 memory. It compares CPU and MAC state after every instruction
against Musashi plus the MAME reference, then compares the physical bus capture
and register snapshots with that host run. It downloads all segment and page
entries and compares those too. The ROM is read back again after execution.

The default budget is 105; `--instructions N` accepts 1..127 so the entire
reset/instruction trace fits. To reproduce the separate generic five-instruction
fixture, use `--machine generic --output build/abc1600-generic`. That older
fixture deliberately pokes a RAM byte at `$80007`; the ABC1600 app obtains its
cause value from its MAC model instead.

Manual ABC1600 operation:

```sh
python3 tools/ice.py --port /dev/cu.usbmodem24301 memory-load \
  --machine abc1600 roms/abc1600/ABC1600ROM.bin
python3 tools/ice.py --port /dev/cu.usbmodem24401 emulate \
  --allow-drive --allow-writes --instructions 105 --prepare
# GO waits for completion; run memory in another terminal after issuing GO.
python3 tools/ice.py --port /dev/cu.usbmodem24401 go
python3 tools/ice.py --port /dev/cu.usbmodem24301 abc1600-memory \
  --allow-drive --samples 4096 --edge release --idle-ms 500 --wait
python3 tools/ice.py --port /dev/cu.usbmodem24401 cpu-registers
python3 tools/ice.py --port /dev/cu.usbmodem24401 cpu-trace
python3 tools/ice.py --port /dev/cu.usbmodem24301 abc1600-status
python3 tools/ice.py --port /dev/cu.usbmodem24301 fetch --capture --output build/abc1600.vcd
```

For generic code, select `memory-load --machine generic FILE`, then run
`memory --boot image` with the existing capture options. `memory-poke` changes
only that generic backend's non-image RAM; it is refused by the ABC1600 app.
CPU writes require `--allow-writes` in either case. Uploads remain volatile
across MCU reset, while saved captures persist in flash. A completed instruction
budget pauses successfully and releases outputs; the next RUN starts with a
new reset rather than resuming the saved PC.

## Instructions and validation

The ROM required these additional instruction families for this milestone:
ADDQ/SUBQ, ANDI (including CCR and supervisor SR forms), SUBA.W/L, DBcc, and
logical shifts LSR/LSL (immediate/register counts and memory forms). They use
the shared effective-address decoder alongside CLR, MOVE/MOVEA, BTST,
BRA/BSR/Bcc, JMP, NOP and the prior limited STOP support. Arithmetic flags,
address-register exceptions to flag/size rules, signed word operands, shift
count edge cases and DBcc counter/condition behavior are tested separately.
The instruction semantics follow Motorola's
[M68000 Programmer's Reference Manual](https://www.nxp.com/docs/en/reference-manual/M68000PRM.pdf).

**81238 instruction cases** compare the firmware core with Musashi in separate
1 MiB host RAM images, checking all D/A registers, PC, SR and every RAM byte.
**17133 MAC accesses** compare the portable memory model with the extracted
MAME methods, including all page entries, task/segment selection, randomized
supervisor/user accesses, protection faults and translated RAM. The reference
address-space shell supplies RAM/open-bus behavior and rejects unimplemented
peripherals; it is not a full MAME machine execution. Native tests also cover
specific bus ordering, flags, illegal modes, upload integrity and model
separation. All 66 repository tests pass.

The physical run verifies 354 ordered byte transfers, 106 complete CPU
snapshots, all MAC tables, final counters, ROM integrity and zero capture
FDEBUG. The trace is sampled on DS release, including valid write data; AS
and DS have independent input synchronization. Upper-bank FC and RESET/HALT
are software observations, not synchronous VCD channels. No extra diagnostic
instructions or stack pushes are inserted into the ROM.

## Keyboard boot milestone (2026-11-17)

The ROM now reaches its input routine at `$0548`, then polls `$7F201`
(physical `$1FF201`, DART channel B RR0) at `$0556`. The loop at
`$0554..$056E` checks bit 0, reads the watchdog cause register, and repeats
while no character is available. No keyboard input is synthesized.

Run `python3 tools/cpu_reference.py --prepare`, then
`python3 tools/abc1600_boot.py` for the bounded host check. Production CPU
execution reaches `$0554` after 552468 instructions. Independent Musashi
execution reaches identical registers and identical RAM/VRAM. Its 575559
instructions differ because video timing uses a bus-access clock and the
interpreters make different reads. This is functional validation, not a
cycle-accurate MAME machine comparison. Another 700 production instructions
verify 100 receive-status polls and 100 watchdog reads.

The added instruction families include MOVEQ, arithmetic/logical operations,
comparisons, immediate arithmetic, bit modification, signed shifts/rotates,
LEA/PEA, JSR/RTS, LINK/UNLK, SWAP/EXT, MOVEM, and word multiply/divide.
The independent matrix now covers 87274 cases, including legal addressing
modes for the new boot-path families. This does not establish full 68000
compatibility or exception support.

The ABC1600 backend adds the CIO universal-bus pointer/reset sequence and
idle ports, DART channel selection and register pointers, idle SCC,
CRTC programming and vertical-sync status, masked VRAM writes, and a bounded
asynchronous functional mover. The generic uploaded-code backend stays separate.
VRAM uses another 512 KiB after the 1 MiB physical RAM allocation in PSRAM.
The mover uses pixel rectangles rather than MAME's separate mask/shift PROMs;
its full hardware behavior remains unverified. RTC/NVRAM input currently reads
high (erased configuration); persistent settings and serial device protocols
remain future work. Interrupts, timers, DMA, disks and populated ABC bus slots
remain unimplemented. Unsupported mapped devices still produce BERR.

The CPU job now accepts up to 2000000 instructions; CPU/ABC1600 memory jobs
accept up to 300000 ms. Other applications retain their previous bounds.
Instruction snapshots still retain the first 128 entries and report the rest
as dropped; the analyzer can retain the last bus window using an unmatched
address trigger. The two-board keyboard run and capture evidence are in
[the validation record](validation/abc1600-keyboard-2026-11-17/README.md).

Ordinary CPU exceptions, divide-zero exceptions, interrupts, prefetch,
remaining opcodes and target-clock synchronization remain later work. Only
the standalone 3.3 V fixture has been validated; motherboard adapter firmware
is separate.
