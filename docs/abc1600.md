# ABC1600: first five instructions

Dispatcher 0.6 executes the first five instructions of the supplied
[ABC1600 ROM](../roms/abc1600/README.md) through the physical PIO byte bus.
The second board holds the uploaded ROM, serves memory, pulses RESET/HALT,
and records state. Instruction snapshots expose the CPU registers without
adding diagnostic instructions to the ROM.

## Image and reset path

The unchanged ROM is `roms/abc1600/ABC1600ROM.bin`, 16 KiB, CRC32 `9372f6f2`.
Its checksum matches boot ROM `6490356-04` in the
[MAME ABC1600 reference](https://github.com/mamedev/mame/blob/master/src/mame/luxor/abc1600_mmu.cpp).
Reset loads SSP `$40000`, A7 `$40000`, PC `$46` and SR `$2700`.

| Instruction PC | Bytes | Instruction | PC after execution, cause `$02` |
| --- | --- | --- | --- |
| `$46` | `4287` | `CLR.L D7` | `$48` |
| `$48` | `1E39 0008 0007` | `MOVE.B ($00080007).L,D7` | `$4E` |
| `$4E` | `0807 0002` | `BTST #2,D7` | `$52` |
| `$52` | `66EC` | `BNE.S $40` | `$54`, branch not taken |
| `$54` | `4286` | `CLR.L D6` | `$56` |

The first data read is the ABC1600 cause register at logical `$80007`.
The MAME reference maps its low address bits to `cause_r()` and returns `$02`
after reset with no reset-button/cause bits set. This fixture supplies a
constant `$02` byte there. With `$06` instead, BTST clears Z, BNE targets `$40`,
and the fifth instruction is `4EF9 0001 0000`, `JMP $00010000`.
Both paths are bench verified. The constant byte does not implement the full
ABC1600 MMU, DMA cause updates, watchdog or peripherals. ROM mirrors and the
actual machine's memory translation remain future work.

On the normal path the final state is PC `$56`, D7 `$02`, D6 zero,
SSP/A7 `$40000`, SR `$2704`, five instructions and zero writes. Twenty-five
byte reads include the eight vector bytes and the `$80007` data byte.
The alternate path ends at PC `$10000`, D7 `$06`, SR `$2700`, after 29 reads.
No instruction at `$56` or `$10000` is executed by this five-instruction job.
The next instruction on the normal path is `5286`, `ADDQ.L #1,D6`, which is
outside this milestone and remains unsupported.

## Load, execute and inspect

```sh
make dispatcher-build
# Program each matching build/multidrop/{1,2}/dispatcher.uf2 on its board.
python3 tools/cpu_reference.py --prepare
python3 tools/abc1600_check.py --cpu /dev/cu.usbmodem24401 \
  --memory /dev/cu.usbmodem24301 --allow-drive
```

The reference command downloads a hash-pinned Musashi archive on first use,
preserves its MIT notices under `build/cpu-reference/`, and builds a separate
host-only library. No Musashi code is linked into firmware. The check uploads
the ROM through the memory tool, verifies CRC and complete USB readback, runs
both cause values, compares each instruction with Musashi, and compares the
hardware register snapshots and every captured byte against the host run.
It finishes on the normal path, paused at PC `$56`, with all outputs released.

For manual operation:

```sh
python3 tools/ice.py --port /dev/cu.usbmodem24301 memory-load roms/abc1600/ABC1600ROM.bin
python3 tools/ice.py --port /dev/cu.usbmodem24301 memory-poke 0x80007 0x02
python3 tools/ice.py --port /dev/cu.usbmodem24401 emulate --allow-drive --instructions 5 --prepare
# Run GO in one terminal, then memory in another; GO waits for completion.
python3 tools/ice.py --port /dev/cu.usbmodem24401 go
python3 tools/ice.py --port /dev/cu.usbmodem24301 memory --allow-drive --boot image \
  --samples 64 --edge release --idle-ms 500 --wait
python3 tools/ice.py --port /dev/cu.usbmodem24401 cpu-registers
python3 tools/ice.py --port /dev/cu.usbmodem24401 cpu-trace
python3 tools/ice.py --port /dev/cu.usbmodem24301 fetch --capture --output build/abc1600.vcd
python3 tools/ice.py --port /dev/cu.usbmodem24301 memory-dump --image \
  --bytes 16384 --output build/abc1600-readback.bin
```

The image occupies a separate 1 MiB target map in PSRAM at `0x11200000`.
Upload clears this map, installs ROM at target address zero, and leaves the
rest as zero-filled RAM. This region does not overlap module staging or
capture rings. Upload is sequential, bounded and CRC checked; incomplete or
corrupted images cannot select the image boot profile. CPU writes to the ROM
range receive BERR. The ROM and RAM survive application loads/RUNs until a
new image upload or MCU reset; neither is persisted in flash. Captures retain
their existing flash persistence.

The CPU now pauses successfully when its instruction budget is exhausted
(CPU state 6, dispatcher job DONE); it releases outputs while preserving
registers. A new RUN/reset starts again; resume from a paused PC is not yet
implemented. Unsupported instructions fail with job error 9, CPU fault 3 and
`instruction_pc`/`opcode` identifying the instruction. CPU writes require the
additional `--allow-writes` opt-in. These five-instruction tests enable no
writes. `BSR` stack writes are tested in host RAM but have not been exercised
as CPU instructions on the physical fixture in this milestone.

## Implemented instruction forms and separate RAM validation

The portable C core now implements CLR, MOVE/MOVEA, BTST, BRA/BSR/Bcc and JMP,
in addition to NOP and the prior limited supervisor STOP support. They use a
shared 68000 effective-address decoder, with byte/word/long sizes as legal,
data/address registers, indirect, postincrement, predecrement, signed
displacements, brief word/long Dn/An indexes, absolute short/long,
PC-relative and immediate operands. Restrictions are checked per instruction.
68020 scaled/full-extension semantics are not enabled. CLR memory performs
the MC68000/68008 read-before-write operation. A7 byte strides use two bytes;
MOVEA.W sign-extends; ordinary byte/word Dn writes preserve upper bits;
BTST uses modulo-32 register and modulo-8 memory bit numbers and changes only
Z. Branches use the opcode-following PC as their displacement base, and BSR
pushes the return address. Supervisor data accesses use FC=5, program/reset
accesses FC=6; user accesses use FC=1/2. Register values remain 32-bit and
external addresses wrap to 20 bits.

The instruction semantics follow Motorola's
[M68000 Programmer's Reference Manual](https://www.nxp.com/docs/en/reference-manual/M68000PRM.pdf),
including legal addressing modes and CLR's read side effect. The independent
Musashi reference is pinned to commit `313ebf1bd9f4d0d93341eb5ce21fd8a119e9dbdd`.

| Independent comparison cases | Count |
| --- | --- |
| CLR sizes, legal EAs, flags | 600 |
| MOVE/MOVEA legal source/destination EA cross-product and data patterns | 29178 |
| Static/dynamic BTST, register selectors and bit-number boundaries | 3332 |
| BRA/BSR/Bcc, all CCR combinations, byte/word displacements | 3584 |
| JMP control EAs | 28 |
| Brief-indexed MOVE, index register/type/size selectors | 864 |
| **Total passed** | **37586** |

For each case, a test-only adapter executes one instruction in two distinct
1 MiB RAM images and compares D0–D7, A0–A7, PC, SR and all RAM bytes. This
tests functional instruction semantics using a 68000 reference; the physical
68008 byte-bus adaptation is checked separately. It does not prove all possible
operand values, exception processing or cycle accuracy. Additional native
tests verify CLR bus reads/writes, long predecrement write order, A7 strides,
FC, invalid EAs, alignment, bus-error termination, BSR stack data, upload bounds,
CRC rejection and the supplied ROM's two five-instruction paths.

## Hardware evidence and limits

Each run records an initial post-reset snapshot and a snapshot after every
instruction attempt. Storage keeps the first 64 snapshots and explicitly
reports any dropped count. Registers include all D/A registers, SR, PC,
SSP/USP, read/write counts and the attempted instruction PC. USB reads require
a stopped job, so no debugger halt or live-state race is involved.

The memory board captures DS-release states through PIO/DMA. Its trace is
compared byte for byte with the host's ordered reset, instruction-extension
and operand reads, with CRC verification and monotonically increasing PIO
timestamps. AS and DS have independent input synchronization; AS can retain
its prior level at the DS-release snapshot. The verifier checks sampled DS
release, ACK, read direction, address and data. Upper-bank FC and reset/HALT
remain software observations rather than synchronous VCD signals.

Recorded results, both bus traces, register snapshots, reference matrix and
tool/firmware hashes are in the
[dated validation record](validation/abc1600-2026-11-17/README.md).
Full exception entry/return, interrupts, prefetch, target clock synchronization,
complete ABC1600 memory hardware and the rest of the opcode set remain
unimplemented. No target CPU performance is promised.
